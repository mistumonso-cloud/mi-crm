# CLAUDE.md

Guía para Claude Code (claude.ai/code) cuando trabaja en este repositorio. Se lee junto
con el `CLAUDE.md` global del usuario — este archivo añade lo específico de este
proyecto y adapta las reglas que dependen del stack real.

**Proyecto:** Vibe Coder CRM
**Versión del documento:** 1.0.0

---

## Reglas Absolutas

1. **MODO PLAN PARA TAREAS NO TRIVIALES**: antes de ejecutar cualquier tarea de 3+ pasos o
   que implique una decisión de arquitectura, entrar en modo plan. Definir pasos de
   ejecución y de verificación. Si algo se rompe durante la ejecución, PARAR y
   replanificar antes de continuar.
2. **BUCLE DE MEJORA CONTINUA**: después de cualquier error en una sesión, registrarlo en
   `.claude/memory/gotchas.md` con fecha, categoría, causa raíz y regla preventiva. Al
   inicio de cada sesión, revisar `gotchas.md` junto con `.claude/memory/MEMORY.md` y con
   la memoria automática entre sesiones. Cuando un patrón alcance 3+ ocurrencias,
   promoverlo a Error Crítico en este archivo.
3. **ESTRATEGIA DE SUBAGENTES**: para problemas complejos, usar subagentes/forks
   agresivamente. Una tarea de investigación, ejecución o análisis por agente. Lanzar
   varios en paralelo cuando las tareas sean independientes.
4. **VERIFICACIÓN ANTES DE DAR POR HECHO**: nunca marcar una tarea como completada sin
   prueba verificable. Correr los checks (`tsc`, `lint`, `build`, Playwright cuando
   aplique), revisar logs y simular el flujo real. Para cambios de UI, abrir el navegador
   y probar a mano — el typecheck y el build no validan la experiencia.
5. **IDIOMA CONTEXTUAL**: comunicación operativa, commits y documentación en español.
   Identificadores técnicos (variables, funciones, tipos, rutas de código) en inglés.
6. **SIN REFERENCIAS A IA**: nunca incluir en commits, código, documentación o PRs
   referencias a la IA que ayudó a producirlos — nada de "Co-Authored-By", nada de
   "Generated by". El trabajo se firma como del dueño del proyecto.
7. **POLÍTICA DE DECISIONES**: nunca decidir stack, arquitectura o dependencias mayores
   sin aprobación explícita del dueño del proyecto. Presentar opciones con pros y
   contras y esperar la decisión. Acciones autónomas permitidas: corrección de bugs,
   refactor menor y actualización de dependencias menores.
8. **CORREGIR LO PROPIO, REPORTAR LO PREEXISTENTE**: todo fallo introducido por el trabajo
   en curso se corrige dentro del mismo cambio. La deuda o los bugs preexistentes que
   aparezcan por el camino se reportan (archivo, línea, impacto) sin ampliar el alcance
   por cuenta propia.
9. **NUNCA HACER PUSH SIN APROBACIÓN EXPLÍCITA**: sin `git push` ni PRs sin confirmación
   previa del dueño del proyecto — ni siquiera un commit de seguimiento trivial en una
   rama ya autorizada. Commits locales sí están permitidos.
10. **FLUJO GIT POR RAMA + PR**: todo cambio entra por rama y PR hacia `main`. Nunca
    commits ni push directo a `main`. Prefijos de rama: `feat/`, `fix/`, `refactor/`,
    `docs/`, `chore/`, `hotfix/`, siempre con el número de ticket de Linear cuando exista
    (`feat/mis-N-slug`). Cada cambio, una rama independiente; tras el merge, se elimina.
11. **SYNC DEL REPO AL INICIO**: `git fetch origin && git pull --rebase` al comenzar cada
    sesión.
12. **VALIDAR ANTES DE PUSH**: correr localmente los mismos checks que exige CI (ver
    Quality Gates) antes de cualquier push o PR.
13. **NUNCA BAJAR VERSIONES DE DEPENDENCIAS** sin aprobación explícita.
14. **ÚLTIMA VERSIÓN ESTABLE**: toda tecnología, framework o librería nueva se instala en
    su última versión estable — salvo Next.js, que este proyecto fija deliberadamente en
    una versión con cambios de última hora (ver nota más abajo).
15. **SKILLS OBLIGATORIOS**: cargar el skill correspondiente antes de tocar la superficie
    de un dominio (tabla más abajo).
16. **SIN SECRETS EN EL REPO**: credenciales solo en `.env.local`/`.env.test.local`
    (gitignored) o en los secrets de GitHub Actions. Secreto filtrado = rotar de
    inmediato.
17. **SEGURIDAD DE DATOS POR DEFECTO (Convex, no RLS)**: este proyecto no usa Postgres/
    Supabase, así que no hay Row Level Security por tabla. El equivalente real: toda
    query o mutation nueva de `convex/*.ts` que toque datos de contactos/ventas/usuarios
    debe llamar `requireRole(ctx, args.token, role)` o `requireUser(ctx, args.token)` (de
    `convex/lib/authz.ts`) como primera línea, sin excepción — igual que ya hacen
    `contacts.ts` y `sales.ts`. Ninguna mutación sensible confía en el cliente sin ese
    check.
18. **VERIFICAR UI DE PLATAFORMAS ANTES DE INSTRUIR**: no dictar pasos de dashboards
    externos (Railway, GitHub, Convex dashboard...) desde memoria; verificar con
    documentación oficial reciente o captura del usuario.
19. **GESTIÓN DEL TRABAJO VÍA ISSUES**: toda tarea de código tiene una issue en Linear
    (equipo `MIS`, proyecto "CRM - MVP") en estado "In Progress" antes de tocar código. El
    PR referencia la issue; solo se marca "Done" cuando el PR está mergeado y enlazado.
20. **UNA PREGUNTA A LA VEZ**: al pedir input al dueño del proyecto, una sola pregunta por
    turno, nunca en lote.

## Memoria del Proyecto

Al comenzar cada sesión, revisar:

- La memoria automática entre sesiones (persistente, fuera del repo).
- `.claude/memory/MEMORY.md` — estado actual, decisiones tomadas, contexto acumulado,
  visible para cualquiera que abra el repo.
- `.claude/memory/gotchas.md` — errores recientes y patrones que evitar (regla 2).

Ambos archivos de `.claude/memory/` se commitean junto con el trabajo cuando cambian.

## Descripción del Proyecto

CRM a medida ("Vibe Coder CRM") para un negocio con dos personas: Carlos (rol `rep`,
operativo — gestión diaria de contactos, home en "Pendientes del día") y Marta (rol
`supervisor`, dueña del negocio — supervisión, home en "Panel de oportunidades"). Sin
alta pública, dos cuentas fijas. Proyecto de aprendizaje/MVP en desarrollo activo,
tracker en Linear (equipo `MIS`, proyecto "CRM - MVP"), desplegado en Railway.

### Nota sobre esta versión de Next.js

Este proyecto fija una versión de Next.js con cambios de última hora — APIs,
convenciones y estructura de archivos pueden diferir de lo que un agente "sepa de
memoria" por su entrenamiento. **Leer la guía correspondiente en
`node_modules/next/dist/docs/` antes de escribir código**, y respetar los avisos de
deprecación. Esta es la razón por la que la Regla 14 (última versión estable) hace una
excepción explícita aquí: la versión está fijada a propósito, no es deuda.

### Convenciones de Código

- **Nombres**: archivos `kebab-case`, componentes `PascalCase`, funciones y variables
  `camelCase`. Identificadores en inglés; comentarios y commits en español.
- **Imports**: alias `@/...` en vez de rutas relativas profundas.
- **Comentarios**: solo para explicar lo que el código no puede decir por sí mismo (una
  restricción, un porqué). Nunca para narrar lo obvio.
- **Nunca `useQuery` de Convex desde un Client Component**: el token de sesión vive solo
  en una cookie `HttpOnly`; todo lo "en vivo" se resuelve con Server Action + `refresh()`
  o `router.refresh()` periódico, nunca con una suscripción de cliente.

## Errores Críticos — NO Repetir

### 1. `fetch` sin comprobar `response.ok`

Un `fetch` que responde 4xx/5xx no lanza excepción: `await fetch(...)` resuelve igual y
el error pasa inadvertido hasta que revienta más adelante con datos vacíos.

```ts
// INCORRECTO — un 500 sigue de largo y data queda undefined
const res = await fetch(url)
const data = await res.json()

// CORRECTO — el error se detecta en el punto donde ocurre
const res = await fetch(url)
if (!res.ok) throw new Error(`HTTP ${res.status} en ${url}`)
const data = await res.json()
```

### 2. `git mv` sobre archivos untracked

`git mv` requiere que el origen ya esté bajo control de versiones. Al instalar código
desde `CODIGO/MIS-N-*/` que mezcla archivos nuevos (untracked) y editados (tracked): o se
hace `git add` de los nuevos primero, o se usa `cp` + `git add` en destino en vez de
`git mv` para los untracked. Nunca encadenar un `rm -rf` inmediatamente después de
comandos cuyo éxito no se verificó de forma independiente, ni siquiera bajo `set -e`.

### 3. `npx convex deploy` es un paso aparte de `npm run build`

`npx convex dev --once` solo empuja a la deployment de **dev**. El build de Next.js/
Railway nunca toca Convex. Cualquier cambio en `convex/schema.ts` o `convex/*.ts`
necesita un `npx convex deploy` explícito a producción justo después de fusionar a
`main`, o el sitio en vivo llama a funciones que no existen en prod.

## Comandos Esenciales

```bash
# Sincronizar
git fetch origin && git pull --rebase

# Flujo rama + PR
git checkout main && git pull --rebase origin main
git checkout -b feat/mis-N-slug
# ... cambios + commits ...
git push origin feat/mis-N-slug        # solo con aprobación (regla 9)
gh pr create --base main --title "..." --body "..."
gh pr merge --squash --delete-branch

# Desarrollo
npm run dev

# Validación local (ANTES de push)
npx tsc --noEmit
npm run lint
npm run build
npx playwright test

# Convex
npx convex dev --once      # push a dev
npx convex deploy          # push a prod (paso aparte, ver Error Crítico 3)
```

## Quality Gates

- `npx tsc --noEmit`, `npm run lint`, `npm run build` en verde.
- Suite Playwright completa (`npx playwright test`) en verde — es la señal de verdad
  real de este repo (CI's `e2e` check también corre esto mismo desde MIS-258).
- Revisión de auditoría GO antes de abrir PR, en tareas con ticket de Linear.
- Para cambios de UI: verificación manual en navegador, escritorio (≥1280px) y móvil
  (320-375px).

## Checklist Pre-Commit

```text
[ ] Trabajo en rama (no main)
[ ] Prefijo de rama válido + número de ticket de Linear si existe
[ ] Typecheck, lint y build pasan localmente
[ ] No hay secrets en el diff
[ ] Toda query/mutation nueva de convex/*.ts pasa por requireRole/requireUser
[ ] Suite Playwright en verde
[ ] UI validada en escritorio y móvil si el cambio toca UI/CSS/layout
[ ] Skill correspondiente cargado antes de tocar su dominio
[ ] Sin referencias a IA en commits, código o docs
[ ] gotchas.md actualizado si hubo algún error en la sesión
[ ] Issue de Linear en "In Progress" antes de tocar código
```
